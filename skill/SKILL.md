# 麦麦套餐折扣排行榜

把麦当劳门店的套餐价格，算成一张**可比较的折扣榜**。

核心不是"列菜单"，而是回答一个问题：**在同一个门店、同一批报价条件下，哪个套餐相对单买最便宜。**

## 何时使用

- 「这家店哪个套餐最划算 / 最便宜 / 折扣最低」
- 「X 套餐打几折 / 比单买省多少」
- 「帮我对比一下这几个套餐」
- 「自取和外送分别哪个套餐值」

**不适用**：热量营养对比、优惠券领取、下单支付、积分抽奖。

## 关键规则（务必遵守）

1. **价格口径**：只用普通可购价（含直接促销，**不含**个人券与付费会员价）。`calculate-price` 若带出券或会员优惠，必须剔除或标注，否则不算折扣。
2. **折扣公式**：`折扣比 = 套餐价 P ÷ 单买合计 D`。单买合计 = 套餐内每个组成单品**单独购买**单价 × 数量之和。赠品不计价。
3. **不混算费用**：`P`、`D` 只含餐品金额。配送费、包装费、服务费**另列**，不摊进单价、不进折扣。
4. **同条件才可比**：组成单品报价必须与套餐同一门店、同一就餐方式、同一时段。条件不一致或未知 → 不可比，不做估算。
5. **缺价即不可比**：任何一个组成单品拿不到有效价格 → 该套餐退出主榜，写明「哪个单品缺价」。**绝不用 0 或估算值填坑。**
6. **排序用未舍入的比值**，展示折数可以舍入；两者不能颠倒。
7. **`P ≥ D` 照实排名**：可以显示「比单买贵 X%」或「与单买同价」，但不加优惠色、不用「省」字。
8. **不制造全覆盖假象**：菜单不全就明说「仅已发现的套餐」，不称「全店最优」。

## 执行流程

用户没给全信息时，先问清：**城市/位置**、**门店**（或"附近最近的一家"）、**自取还是外送**。

### 第 1 步｜确定门店

- **到店自取**：`query-nearby-stores`（入参用用户给的位置或区域名）
- **外送**：`delivery-query-addresses` 取地址 → `delivery-query-stores` 取可配送门店
- 门店多于一个且用户没指定时，列出前 3 个让用户选，**不要替用户决定**。

### 第 2 步｜拉菜单

`query-meals`，**四个参数都要传**（实测漏传会报 `600058`）：

```
{ "beType": 1, "orderType": 1, "storeCode": "<门店编码>" }
```

- `beType`：1=到店取餐，2=麦乐送，5=得来速，6=企业团餐
- `orderType`：1=到店，2=外送
- 结果里 `data.meals` 是**以餐品编码为键的对象**（不是数组），`data.categories[].meals` 只是 `{code, tags}` 索引。

**只挑套餐类餐品**：名称含「套餐 / **三件套 / 四件套** / 组合 / 超值 / 随心选 / 拼盘 / 双人 / 家庭 / 桶」。

> 踩坑记录：麦当劳的主力套餐叫「巨无霸三件套」「人气超值四件套随心选」，**不含「套餐」二字**。只按「套餐」筛会漏掉 28 个，务必按上面的完整口径。

单品不进榜，但它们是单买合计的来源。

### 第 3 步｜取套餐组成

`query-meal-detail`，需 `beType` + `orderType` + `storeCode` + `code`（套餐编码）：

```
{ "beType": 1, "orderType": 1, "storeCode": "<门店编码>", "code": "<套餐编码>" }
```

组成在 `data.rounds[].choices[]`，**只取 `isDefault=1` 的选项**才是默认组成（`isDefault=0` 是可换购项，不能算进去）。

**有界限制**：一次请求最多分析 **15 个套餐**（同门店组件可复用核价结果），并在报告里注明「本次分析了 N 个套餐，非全量」。

### 第 4 步｜逐项核价

`calculate-price`，同样需要 `beType` + `orderType` + `storeCode`，商品列表格式为：

```json
{ "items": [{ "productCode": "<编码>", "quantity": 1 }] }
```

对**套餐本身**和**每个组成单品**分别调用：

- 套餐：`items=[{productCode: 套餐编码, quantity: 1}]` → `data.price` 就是套餐价 `P`（**单位是分**）
- 单买：每个组成单品单独成单 → 取 `data.price`（分）

**已知坑**：部分组成码是「套餐内专属码」，单独立项会返回 `price=0` 且 `productList` 为空（例如可乐 `3050`）。此时按顺序处理：

1. 查菜单里该码的 `currentPrice`
2. 找**唯一同名零售单品**的菜单价（有歧义就不猜）
3. 都没辙 → 该套餐判「组成单品缺价」，退出主榜

用 `node scripts/live/rank.js` 计算时会自动做上面三步，并披露「按同名匹配补价」的条数。加 `--strict` 可只用可核价单品。

**同一次请求内最多 40 次 `calculate-price`**。超限就减少套餐数量，**不要**靠估算补齐。

### 第 5 步｜落盘原始数据

把每个工具的原始返回写到 `.mcd-live/raw/` 下，文件名固定：

```
.mcd-live/raw/stores.json          query-nearby-stores 或 delivery-query-stores
.mcd-live/raw/meals.json           query-meals
.mcd-live/raw/detail-<餐品编码>.json  query-meal-detail
.mcd-live/raw/price-<编码>-combo.json calculate-price（套餐）
.mcd-live/raw/price-<编码>-single.json calculate-price（单买）
```

**原样保存，不要改写字段**。后续步骤依赖这些文件，且它们是审计证据。

### 第 6 步｜计算排名

在项目根目录运行：

```bash
node scripts/live/rank.js .mcd-live/raw --channel pickup --out .mcd-live/out
```

脚本会：
- 用 `src/core` 的资格判定、折扣公式、竞争排名、覆盖统计（与单元测试同一套规则）计算；
- 产出 `.mcd-live/out/result.json`（结构化结果）与 `.mcd-live/out/report.html`（可分享报告页）。

字段对不上时会**直接报错并列出它实际看到的键名**，此时把错误信息反馈给用户，不要猜着改。

### 第 7 步｜呈现结果

给用户：
1. 一句结论（「最划算的是 X，6.0 折，比单买省 ¥18.40」）
2. 前 3 名（名称 / 折数 / 套餐价 / 单买合计 / 省多少）
3. 「暂不可比较」的套餐 + 原因（缺价、售罄、条件不明）
4. 报告链接：`.mcd-live/out/report.html`
5. 一句话口径说明：普通可购价、不含券与会员价、报价时间为本次查询时刻

## 输出与语气

- 数字带单位，金额两位小数，折数写成「6.0 折」而不是「60%」。
- 不夸大：不可比就说不可比，缺价就说缺价。
- 不推荐下单、不替用户决定买什么，只给比较结果。

## 合规边界（必须守住）

- **一次用户请求 = 一轮查询**。不设定时器、不做后台轮询、不跨会话缓存抓取。
- 不重试失败的调用（失败就记 unknown，继续算其它套餐）。
- 单个请求内工具调用总数**不超过 60 次**。
- Token 只存在于 MCP 客户端配置（环境变量），**不写进任何文件、日志、报告**。
- 报告与代码里不得出现真实门店详细地址：外送地址只显示别名（如「公司」「家」）。
